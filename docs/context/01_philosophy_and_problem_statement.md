# 01. الفلسفة المعمارية ومبررات وجود حزمة `context`

تعتبر حزمة `context` في لغة Go من أذكى وأبسط الحلول الهندسية التي واجهت واحدة من أعقد المشاكل في النظم الموزعة والمتزامنة: **كيف نتحكم في دورة حياة العمليات البرمجية المتشعبة عبر مئات الـ Goroutines وحدود الشبكات دون التسبب في تسريب الموارد أو حدوث سباقات بيانات (Data Races)؟**

---

## ⏳ السياق التاريخي ونشأة الحزمة

في الإصدارات الأولى من لغة Go (ما قبل 2014)، لم تكن المكتبة القياسية تحتوي على مفهوم موحد للسياق أو الإلغاء. كان المطورون يعتمدون على:

1. تمرير قنوات مخصصة مثل `done chan struct{}` يدوياً بين الدوال.
2. استخدام متغيرات منطقية (Booleans) محمية بأقفال (`sync.Mutex`).
3. ترك الـ Goroutines تعمل حتى تنهي عملها حتى لو أغلقت بوابة العميل الاتصال (`Client Disconnect`).

في عام 2014، قام **Sameer Ajmani** وفريق البنية التحتية في Google بنشر مقال ثوري بعنوان *"Go Concurrency Patterns: Context"* وأطلقوا حزمة خارجية باسم `golang.org/x/net/context`. بعد نجاحها الباهر في توحيد خدمات Google وشركات التقنية العالمية، تم دمجها رسمياً في صلب المكتبة القياسية مع إصدار **Go 1.7** في عام 2016، وأصبحت واجهة التخاطب الإلزامية لكافة حزم الشبكات، وقواعد البيانات (`database/sql`)، والخوادم (`net/http`).

---

## 🛑 المشاكل الجوهرية الخمس التي تحلها حزمة `context`

### 1. معضلة تسريب الـ Goroutines والذاكرة (Goroutine & Memory Leaks)

#### المشكلة

في لغة Go، الـ Goroutines رخيصة جداً من حيث استهلاك الذاكرة (تبدأ بـ 2KB تقريباً)، مما يغري المطورين بإطلاق الآلاف منها. ولكن:
> **جامع القمامة (Garbage Collector) في Go لا يمكنه أبداً إيقاف أو تنظيف Goroutine نشطة تنتظر على قناة (Channel) أو عملية إدخال/إخراج (I/O Blocked)، حتى لو أصبحت نتائجها غير مرغوبة!**

إذا قام عميل HTTP بطلب تقرير مالي معقد يستغرق 30 ثانية، ثم أغلق المتصفح بعد ثانيتين، فإن الخادم إذا لم يكن يراقب الإلغاء، سيظل يشغل استعلامات قاعدة البيانات، ويستهلك المعالج والذاكرة لحساب تقرير لن يقرأه أحد. ومع تكرار ذلك، تتراكم ملايين الـ Goroutines المعلقة في الذاكرة حتى ينهار الخادم بفعل نفاد الذاكرة (Out Of Memory Crash).

#### الحل عبر `context`

توفر الحزمة قناة إلغاء قياسية يتم الاستماع إليها عبر `select`:

```go
select {
case <-ctx.Done():
    // تم إلغاء الطلب من العميل أو انتهت المهلة!
    // توقف فوراً، حرر المقابس والموارد، واخرج بسلام لمنع التسريب
    return ctx.Err()
case result := <-workChan:
    return process(result)
}
```

### 2. الإلغاء الشلالي الموزع (Cascading Distributed Cancellation)

#### المشكلة

في الأنظمة متعددة الطبقات (Microservices أو المعمارية النظيفة)، الطلب الواحد يتفرع إلى شجرة استدعاءات:

```text
HTTP Request ──► Auth Service ──► User Service ──► Cache (Redis)
                                               └──► DB (Postgres)
```

إذا فشل التحقق في `Auth Service`، أو انقطع اتصال العميل، فمن الهدر الكارثي استمرار العمليات الفرعية في `User Service` و `Postgres`. كيف يتم إخطار كافة الأبناء والأحفاد بالتوقف دون ربط صلب (Coupling) ودون كتابة خوارزميات إشعار معقدة؟

#### الحل عبر `context`

تعتمد الحزمة على هيكل **شجرة هرمية (Hierarchical Tree)**:

- عند إلغاء سياق الأب (`Parent Context`)، تنتشر إشارة الإلغاء تلقائياً وشلالياً إلى كافة السياقات المشتقة منه (`Child Contexts`) فوراً وبشكل متزامن وخيطي آمن.
- لا يمكن للابن أبداً إلغاء أبيه (الاتجاه أحادي دائماً من الأعلى للأسفل).

```text
               Parent (مُلغى ❌)
               ┌──────┴──────┐
               ▼             ▼
          Child 1 ❌     Child 2 ❌
          ┌────┴────┐        │
          ▼         ▼        ▼
       Grandchild Grandchild Grandchild ❌
```

### 3. إدارة الميزانيات الزمنية المتناقصة (Deadline & Timeout Budgeting)

#### المشكلة

عند استدعاء خدمة خارجية أو استعلام قاعدة بيانات، غالباً ما يحدد المهندس مهلة ثابتة (مثل 5 ثوانٍ لكل عملية). ولكن في سلسلة من العمليات:

- العملية A تستغرق 4 ثوانٍ.
- العملية B تبدأ وتمنح نفسها 5 ثوانٍ جديدة!
- النتيجة: انتهت مهلة العميل الأصلية، بينما الخدمات الخلفية ما زالت تواصل محاولات محكوم عليها بالفشل.

#### الحل عبر `context`

تدعم الحزمة خاصية **المواعيد النهائية الثابتة (`Deadlines`)**:

- إذا كان الأب يملك مهلة تنتهي بعد 3 ثوانٍ، وحاول الابن إنشاء مهلة بـ 10 ثوانٍ، فإن الحزمة ترصد بذكاء أن مهلة الأب أقرب، فتلتزم بمهلة الأب تلقائياً (`Earliest Deadline Wins`).
- يمكن لأي دالة في أي عمق من الشجرة استدعاء `ctx.Deadline()` لمعرفة الوقت المتبقي وحساب ميزانيتها (Budgeting) قبل الشروع في استعلامات مكلفة.

### 4. تمرير البيانات المقتصرة على دورة الطلب (Request-Scoped Metadata)

#### المشكلة

تتطلب بنية الخدمات الحديثة تمرير بيانات عامة مشتركة عبر جميع الطبقات، مثل:

- معرّف الطلب التشخيصي (`Request ID` / `Correlation ID`).
- معرّف المستأجر لعزل البيانات (`Tenant ID`).
- رمز التوثيق وصلاحيات المستخدم (`User Principal`).

إذا قمنا بتمرير هذه القيم كمعاملات صريحة في كل دالة:

```go
// تلوث كارثي لتواقيع الدوال وهياكل الطبقات
func GetOrder(tenantID, reqID, userID, orderID string) (*Order, error)
```

يصبح الكود صلباً ومستحيلاً للصيانة، وتتلوث طبقة الـ Domain والـ Storage بتفاصيل بروتوكول النقل. وفي نفس الوقت، لغة Go **لا تدعم ولا تحبذ** التخزين المحلي للخيوط (Thread-Local Storage - TLS) لأنه يتعارض مع مرونة جدولة الـ Goroutines عبر الـ OS Threads.

#### الحل عبر `context`

استخدام `context.WithValue`:

- حاوية خيطية آمنة (Thread-Safe) غير قابلة للتعديل.
- ترافق الطلب في مساره الكامل عبر الدوال والـ Goroutines.
- تقتصر على عمر الطلب فقط؛ بمجرد انتهاء الطلب تتلاشى البيانات ويفرغها جامع القمامة تلقائياً.

---

### 5. عزل العمليات غير المتزامنة والمهام الخلفية (`Detached Execution`)

#### المشكلة في الإصدارات السابقة

في Go 1.19 وما قبلها، عندما يحتاج الخادم لإطلاق مهمة خلفية بعد إرسال الرد للعميل (مثل تسجيل تدقيق أمني `Audit Logging` أو تحديث كاش):

- إذا مرر المطور `r.Context()`، ستفشل المهمة الخلفية فوراً لأن خادم HTTP يلغي سياق الطلب بمجرد خروج دالة الـ Handler.
- إذا أنشأ المطور سياقاً جديداً تماماً عبر `context.Background()`، يفقد كافة بيانات التتبع (`Trace ID`, `Tenant ID`) التي كانت مرافقة للطلب الأصلي!

#### الحل الحديث في Go 1.20+

إضافة دالة `context.WithoutCancel(parent)`:

- تفصل سياق الابن عن قنوات الإلغاء والمهل الزمنية للأب.
- تحتفظ بكافة البيانات والسمات (`Values`) المخزنة في سياق الأب.

## 🏛️ الفلسفة المعمارية الثلاثية لحزمة `context`

تستند حزمة `context` في صميمها إلى 3 مبادئ معمارية صارمة شكلت هوية لغة Go:

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │                      المبادئ المعمارية الصارمة                         │
 ├────────────────────────────────────────────────────────────────────────┤
 │ 1. عدم القابلية للتعديل (Immutability): شجرة اشتقاق تراكمية أحادية.     │
 │ 2. التمرير الصريح (Explicit Propagation): تمرير ctx كأول معامل دائماً.  │
 │ 3. الأمان التزامني الأصيل (Inherent Thread Safety): التزامن دون أقفال خارجية. │
 └────────────────────────────────────────────────────────────────────────┘
```

### أولاً: عدم القابلية للتعديل (Immutability by Derivation)

لا توجد أي دالة في حزمة `context` تتيح تعديل كائن سياق موجود (`No Mutators`). بدلاً من ذلك، كل استدعاء (`WithCancel`, `WithValue`, `WithTimeout`) يقوم باشتقاق كائن سياق جديد تماماً يلتف حول الأب (`Wrapping / Decoration Pattern`).

- هذا يضمن أن الأب محمي تماماً من أي آثار جانبية يفتعلها الأبناء.
- يتيح مشاركة نفس كائن السياق بأمان تام بين آلاف الـ Goroutines دون أي خوف من تعديل البيانات.

### ثانياً: التمرير الصريح (Explicit Propagation vs Hidden Magic)

ترفض فلسفة Go التخزين الخفي السحري للمعلومات (مثل Thread-Local Variables في Java أو AsyncLocalStorage في Node.js).

- وجود السياق صراحة في أول توقيع الدالة: `func Do(ctx context.Context, ...)` يوضح للمهندس وقارئ الكود ومحللات الكود الثابتة (`Static Analyzers`) أن هذه العملية قابلة للإلغاء، محكومة بمهلة زمنية، وتخضع لرقابة دورة الحياة.

### ثالثاً: الأمان التزامني الأصيل (Concurrent Safety)

كافة دوال واجهة `context.Context` صُممت لتكون آمنة بطبيعتها للاستدعاء المتزامن والمتكرر من مئات الـ Goroutines في آن واحد دون الحاجة لأي مزامنة إضافية من المستخدم (`Simultaneous Goroutine Safety`).
