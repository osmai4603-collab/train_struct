# 01. المعمارية وهرم الاختبارات في أنظمة Go الموزعة

## 1. فلسفة الاختبار في منظومة Go

في معظم لغات البرمجة الشائعة (مثل Java مع JUnit، أو Ruby مع RSpec، أو JavaScript مع Jest)، يتم التعامل مع الاختبارات كلغة نطاق منفصلة (DSL) تعتمد على الـ Annotations، والتسجيل التلقائي، والانعكاس (Reflection)، وتداخل أطر العمل.

في المقابل، صُممت منظومة الاختبار في Go وفق مبادئ هندسية متشددة وضعها مبتكرو اللغة:

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   المبادئ الفلسفية للاختبار في Go                      │
├───────────────────────────────────┬────────────────────────────────────┤
│ مبدأ "الاختبار كود عادي"          │ مبدأ "اختبار الحالة والسلوك"       │
│ (Tests are Ordinary Go Code)      │ (State & Behavior over Interaction)│
├───────────────────────────────────┼────────────────────────────────────┤
│ • لا توجد أطر عمل سحرية.          │ • نختبر ماذا يفعل النظام وليس كيف   │
│ • التحكم يتم عبر if و for و switch│   ينفذه داخلياً.                   │
│ • فحص الأخطاء يتم بقيم صريحة      │ • لا نهتم بعدد مرات استدعاء الدوال │
│   err != nil وليس عبر استثناءات.  │   الخاصة إذا كانت النتيجة صحيحة.   │
├───────────────────────────────────┼────────────────────────────────────┤
│ مبدأ "الفشل التشخيصي الواضح"      │ مبدأ "استمرارية الفحص"             │
│ (Actionable Diagnostic Failure)   │ (Keep Going on Failure)            │
├───────────────────────────────────┼────────────────────────────────────┤
│ • رسالة الفشل يجب أن تكشف السبب   │ • نفضل t.Errorf على t.Fatalf لكي   │
│   والمدخلات والمتوقع فوراً.        │   تظهر كل الفحوصات الفاشلة في دورة │
│ • صيغة Got before Want القياسية.  │   واحدة دون الحاجة لإعادة التشغيل. │
└───────────────────────────────────┴────────────────────────────────────┘
```

## 2. هرم الاختبارات المعدل للمشاريع والخدمات الميكروية (The Pragmatic Test Pyramid)

في الأنظمة الموزعة (Microservices Architecture)، لا ينطبق هرم الاختبارات التقليدي الساذج (الذي يفترض أن تكون 95% اختبارات وحدة منعزلة تماماً و 5% اختبارات أخرى). في الأنظمة الحقيقية:

- اختبار الوحدة المعزول لا يضمن صحة استعلامات PostgreSQL المعقدة.
- اختبار الوحدة لا يكشف مشاكل تسلسل الـ JSON أو قيود المفاتيح الأجنبية.

لذلك، تعتمد الشركات الكبرى **الهرم العملي المعدل**:

```text
               ┌───────────────────────┐
               │    E2E & Smoke Tests  │  (~5-10%)
               │  مسارات العمل الحرجة   │  (بطيئة، بيئات شبه إنتاجية)
               └───────────┬───────────┘
                           │
             ┌─────────────┴─────────────┐
             │ Integration Tests (Docker)│  (~30-40%)
             │  Testcontainers & Postgres│  (سريعة، واقعية، حقيقية)
             └─────────────┬─────────────┘
                           │
           ┌───────────────┴───────────────┐
           │   Unit Tests & Table-Driven   │  (~50-60%)
           │ المنطق الحسابي، الحزم، Fakes  │  (فائقة السرعة، موازية تماماً)
           └───────────────────────────────┘
```

## 3. مقارنة تفصيلية بين أساليب الاختبار

### 3.1 الاختبار القائم على الحالة (State-Based Testing) - الموصى به

في هذا النمط، نقوم بتجهيز المدخلات، تنفيذ العملية، ثم فحص الحالة النهائية للنظام أو القيمة المعادة:

```go
// نمط سليم ومستقر: اختبار الحالة والسلوك
func TestWallet_Deposit(t *testing.T) {
    wallet := NewWallet()
    err := wallet.Deposit(100)
    if err != nil {
        t.Fatalf("Deposit(100) unexpected error: %v", err)
    }

    if got, want := wallet.Balance(), 100; got != want {
        t.Errorf("wallet.Balance() = %d, want %d", got, want)
    }
}
```

**الميزة الهندسية:** إذا قمنا بإعادة هيكلة الكود الداخلي للمحفظة (مثلاً استخدام بنية بيانات مختلفة أو تسجيل المعاملات في جدول فرعي)، سيبقى الاختبار ناجحاً طالما أن النتيجة النهائية صحيحة.

### 3.2 الاختبار القائم على التفاعل (Interaction-Based Testing) - غير محبذ

في هذا النمط، نستخدم أدوات المحاكاة (Mocks) للتحقق من أن دالة معينة تم استدعاؤها مرتين وبترتيب محدد:

```go
// ❌ نمط هش (Brittle): يرتبط بتفاصيل التنفيذ الداخلي
func TestWallet_Deposit_Mocked(t *testing.T) {
    mockStore := new(MockStore)
    // إلزام الكود باستدعاء UpdateBalance مرة واحدة بالضبط
    mockStore.On("UpdateBalance", 100).Return(nil).Once()

    wallet := NewWalletWithStore(mockStore)
    _ = wallet.Deposit(100)
    mockStore.AssertExpectations(t)
}
```

**الخطر الهندسي:** إذا قرر المطور دمج عمليتين في استدعاء واحد، أو إضافة كاش، أو تغيير التابع الداخلي، سيفشل الاختبار فوراً بالرغم من أن الرصيد سليم بنسبة 100%!
