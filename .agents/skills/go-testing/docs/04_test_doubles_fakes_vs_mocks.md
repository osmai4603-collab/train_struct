# 04. بدائل الاختبار: Fakes مقابل Mocks وتصميم الواجهات

## 1. تصنيف بدائل الاختبار (Test Doubles Taxonomy)

استناداً إلى معايير هندسة البرمجيات في Google (SWE Book: Chapter 13)، تنقسم بدائل الاختبار إلى خمسة أنواع أساسية:

1. **Dummy:** كائن يمرر فقط لتلبية متطلبات معاملات الدالة (مثل سياق فارغ أو معرّف لا يُستخدم).
2. **Stub:** كائن يعيد إجابات ثابتة ومعدة مسبقاً (Canned responses) دون أي منطق داخلي.
3. **Spy:** كائن يسجل العمليات والمعاملات التي تم تمريرها إليه لتمكين الاختبار من التحقق منها لاحقاً.
4. **Mock:** كائن مبرمج مسبقاً بقائمة من التوقعات الدقيقة (Expectations) ويفشل الاختبار إذا تم استدعاؤه بشكل مختلف أو بعدد مختلف.
5. **Fake:** تطبيق برمجي حقيقي وبسيط وخفيف للواجهة (في الذاكرة غالباً)، يحاكي السلوك الكامل للخدمة الحقيقية دون الاعتماد على بنية تحتية ثقيلة.

## 3. مبدأ تصميم الواجهات في Go: "المستهلك هو من يحدد الواجهة"

من الأخطاء الكبرى في Go أن تقوم الحزمة المزودة (Producer) بتعريف واجهة ضخمة لكل توابعها:

```go
// ❌ خطأ فادح: تضخم الواجهات من جانب المنتج
package storage

type HeavyDatabaseInterface interface {
    CreateUser(...)
    DeleteUser(...)
    ListInvoices(...)
    CreateOrder(...)
    // ... 50 تابعاً آخر!
}
```

القاعدة المعيارية في Go: **الواجهات في Go ضمنية (Implicit Interfaces)**. لذلك يجب على الحزمة المستهلكة (Consumer) تعريف واجهة صغيرة تضم فقط ما تحتاجه:

```go
//  المعيار السليم: واجهة مصغرة ومخصصة لخدمة الطلبات
package orders

import "context"

type UserValidator interface {
    IsUserActive(ctx context.Context, userID string) (bool, error)
}

type OrderService struct {
    validator UserValidator // يسهل جداً توفير Fake بسيط لهذا التابع فقط
}
```

## 4. متى تصبح الـ Mocks/Spies ضرورية؟

تكون الـ Mocks أو الـ Spies مقبولة هندسياً فقط عند التحقق من **الآثار الجانبية الخارجية غير القابلة للرصد المباشر (Unobservable Side Effects)**:

- إرسال بريد إلكتروني تنبيهي عبر بوابة خارجية (AWS SES / SendGrid).
- إرسال إشعار دفع (Push Notification).
- إرسال حدث إلى وسيط رسائل خارجي (Kafka / RabbitMQ) لا يمكن فحص حالته محلياً.
