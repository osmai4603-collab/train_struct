# 01. معمارية منظومة JOSE وتصنيف أنواع ومستويات الـ JWT

## 1. عائلة معايير JOSE وتكاملها

في المشاريع الكبيرة، لا يُنظر إلى الـ JWT كأداة نصية معزولة، بل كجزء بنيوي من منظومة بروتوكولات **JOSE (JSON Object Signing and Encryption)** المعرفة رسمياً عبر IETF:

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        عائلة معايير JOSE                              │
├──────────────────┬──────────────────┬──────────────────┬───────────────┤
│ 1. RFC 7519      │ 2. RFC 7515      │ 3. RFC 7516      │ 4. RFC 7517   │
│       JWT        │       JWS        │       JWE        │     JWK/JWKS  │
│                  │                  │                  │               │
│ تنسيق الادعاءات  │ التوقيع الرقمي   │ التشفير والسرية  │ تمثيل المفاتيح│
│ (JSON Claims)    │ والتحقق من النزاهة│ لحماية البيانات  │ ومجموعاتها    │
└──────────────────┴──────────────────┴──────────────────┴───────────────┘
                                   │
                     ┌─────────────▼─────────────┐
                     │        RFC 7518: JWA      │
                     │ خوارزميات التشفير والتوقيع │
                     │   (RS256, EdDSA, A256GCM) │
                     └───────────────────────────┘
```

## 2. المستويات التشفيرية (Cryptographic Tiers)

### 2.1 الرموز غير المؤمنة (Unsecured Tokens — `alg: "none"`)
- البنية: `Header.Payload.` (بدون توقيع إطلاقاً).
- الحكم الإنتاجي: **ممنوع قطعياً.**
- القاعدة الهندسية: خادم Go يجب أن يسقط فوراً أي رمز يحمل `"alg": "none"` حتى لو كان الطلب قادماً من شبكة محلية.

### 2.2 الرموز الموقعة رقمياً (JWS — Signed JWTs)
- البنية: `Base64URL(Header) . Base64URL(Payload) . Base64URL(Signature)`
- الهدف: إثبات الهوية وسلامة البيانات.
- التحذير الأمني: **الحمولة غير مشفرة!** أي شخص يحصل على الرمز يستطيع فك ترميز Base64 وقراءة كافة الادعاءات.

### 2.3 الرموز المشفرة (JWE — Encrypted JWTs — RFC 7516)
- البنية المادية (5 أجزاء):
  `ProtectedHeader . EncryptedKey . IV . Ciphertext . AuthenticationTag`
- خوارزميات التشفير المزدوجة:
  - إدارة مفتاح المحتوى (Key Management): تشفير المفتاح المتماثل المؤقت بمفتاح المتلقي العام (مثل `RSA-OAEP-256` أو `ECDH-ES`).
  - تشفير المحتوى (Content Encryption): تشفير الحمولة بتشفير متماثل فائق السرعة وموثق مسبقاً (مثل `A256GCM` أو `ChaCha20-Poly1305`).
- حالات الاستخدام: حماية البيانات الشخصية والمالية (PII/HIPAA/GDPR) وإخفاء المعرفات الداخلية للنظام.

### 2.4 الرموز المركبة / المتداخلة (Nested JWTs: Sign-then-Encrypt)
- النمط المعياري: توقيع الحمولة بـ JWS أولاً لإثبات هوية وموثوقية المصدر، ثم تشفير ناتج الـ JWS كاملاً داخل JWE.
- النتيجة: سرية تامة أثناء النقل، ونزاهة وهوية مثبتة لا يمكن تزويرها حتى لو تمكن طرف ثالث من فك التشفير الخارجي.

## 3. المستويات والأدوار المعمارية (Architectural Roles & Lifecycles)

```text
┌────────────────────────────────────────────────────────────────────────┐
│                   الأدوار المعمارية للرموز في النظام الموزع             │
├──────────────────────┬─────────────────────────┬───────────────────────┤
│ الدور المعماري        │ المتلقي المستهدف        │ العمر الافتراضي الموصى │
├──────────────────────┼─────────────────────────┼───────────────────────┤
│ 1. ID Token          │ العميل (Frontend/App)   │ 15 - 60 دقيقة         │
│ 2. Access Token      │ خوادم الموارد (APIs)    │ 5 - 15 دقيقة          │
│ 3. Refresh Token     │ خادم المصادقة حصراً      │ 1 - 30 يوماً (مع RTR) │
│ 4. DPoP / mTLS Token │ APIs مع ربط بصمة المفتاح│ 5 - 15 دقيقة          │
│ 5. Action Token      │ عملية محددة (Reset/Act) │ 5 - 15 دقيقة          │
│ 6. M2M / S2S Token   │ الخدمات الداخلية        │ 15 - 60 دقيقة         │
└──────────────────────┴─────────────────────────┴───────────────────────┘
```

### التفاصيل الهندسية للأدوار:

1. **ID Token (OpenID Connect):** مخصص حصراً للواجهة الأمامية لتخصيص واجهة المستخدم. **يُحظر قبوله كرمز تفويض في مسارات الـ API.**
2. **Access Token (RFC 9068):** رمز مدمج ذاتياً يحمل نطاقات الصلاحيات (`scope`) ومعرف المستخدم (`sub`) ومعرف الجمهور (`aud`). يجب أن يكون عمره قصيراً لتقليل نافذة استغلال الرمز المسروق.
3. **Refresh Token (تدوير الجلسات):** رمز طويل الأجل يُستخدم فقط لطلب Access Token جديد. يخضع لنظام **Refresh Token Rotation (RTR)** بحيث يُلغى فور استخدامه وتصدر عائلة جديدة.
4. **Sender-Constrained Tokens (إثبات الحيازة - Proof of Possession):**
   - **DPoP (RFC 9449):** يوقع العميل ترويسة DPoP بمفتاحه الخاص المحلي، ويربط خادم Go رمز الوصول ببصمة المفتاح العام في الحقل `cnf.jkt`. حتى لو سُرق الرمز، يعجز المهاجم عن استخدامه لغياب المفتاح الخاص.
   - **mTLS (RFC 8705):** يربط الرمز ببصمة شهادة الـ X.509 في الاتصال المشفر بين الميكروسيرفيسز عبر الحقل `cnf.x5t#S256`.
5. **Ephemeral Action Tokens:** رموز مخصصة لغرض واحد (تفعيل الحساب، استعادة كلمة المرور، الموافقة على تحويل بنكي). تحمل `jti` فريداً يُستهلك لمرة واحدة وتلغى صلاحيتها تلقائياً عند تغيير كلمة المرور عبر ربطها بـ User Token Epoch.
6. **Machine-to-Machine (M2M) Tokens:** لتبادل البيانات بين الخدمات المصغرة بدون وسيط بشري عبر معيار OAuth2 Client Credentials أو بروتوكول SPIFFE/SPIRE (JWT-SVID).
