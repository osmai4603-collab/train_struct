# مصفوفة الأنماط المضادة في التعامل مع الأخطاء (Anti-Patterns Matrix)

| النمط المضاد (Anti-Pattern) | لماذا يُعد خطيراً؟ | البديل الصحيح والحل المعياري |
| :--- | :--- | :--- |
| **سجل وأرجع (Log and Return)** | تكرار نفس الخطأ في السجلات عدة مرات، وتشويه مسار تتبع الحوادث والتحليلات. | **إما أن تسجل وتعالج (Handle & Log) أو تغلف وترجع (Wrap & Return)** — لا تجمعهما أبداً. |
| **المقارنة المباشرة `err == Sentinel`** | تفشل المقارنة بمجرد تغليف الخطأ بواسطة `%w` في أي دالة وسيطة. | استخدم دائماً `errors.Is(err, TargetSentinel)`. |
| **مطابقة النصوص (String Matching)** | سهلة الكسر والهشاشة عند أي تعديل طفيف على صياغة رسالة الخطأ أو تحديث مكتبة. | استخدم `errors.Is`، أو استخراج النوع بـ `errors.As`، أو فحص السلوك (Behavior Assertion). |
| **تسريب أخطاء البنية التحتية** | يؤدي إلى اقتران طبقات الخدمة والواجهة ببرامج تشغيل محددة (مثل Postgres أو Redis driver). | ترجمة أخطاء البنية التحتية في طبقة الـ Repository إلى أخطاء نطاق (`platformerr.NotFound` / `Internal`). |
| **تجاهل الأخطاء عبر المعرّف الفارغ (`_ =`)** | إخفاء حالات فشل إغلاق الموارد أو كتابة البيانات بصمت، مما يسبب تسريب اتصالات وتلف بيانات. | فحص الخطأ، أو جمعه مع أخطاء أخرى عبر `errors.Join`، أو تسجيله كـ Debug log على الأقل. |
| **تسريب البيانات الحساسة (PII Leaks)** | كشف كلمات المرور، رموز المصادقة، أو عناوين الشبكة الداخلية في السجلات أو ردود HTTP. | تنقية معاملات `fmt.Errorf` وحجب التفاصيل الفنية عن ردود المستخدم النهائي (`platformerr.WriteHTTPError`). |
| **بدء الخطأ بحرف كبير أو إنهائه بنقطة** | مخالف لمعايير Go الرسمية (`Code Review Comments`) ويجعل نصوص التغليف مشوهة بصرياً. | اكتب رسائل الخطأ دائماً بحروف صغيرة وبدون علامات ترقيم نهائية: `errors.New("record not found")`. |
| **استخدام `panic` كبديل لتدفق الأخطاء** | إسقاط خادم الويب وانهيار العملية بالكامل دون مبرر منطقي. | إرجاع `error` في كل المسارات العادية، وحصر `panic` في مرحلة الإقلاع (Startup) أو الحالات المستحيلة برمجياً، مع تأمين خوادم HTTP بـ Recovery Middleware. |
