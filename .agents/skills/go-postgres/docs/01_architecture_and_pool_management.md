# الدليل المعماري 01: معمارية الطبقة وإدارة مجمع الاتصالات (`pgxpool`)

## 1. التموضع والمسؤوليات المعمارية

في أي مشروع Go مصمم وفق معمارية برمجية متقدمة (Clean Architecture / Ports & Adapters)، تتوزع وظائف التخزين على طبقتين منفصلتين:

1. **طبقة البنية التحتية العامة (`internal/infrastructure/postgres`)**:
   - مسؤولة عن إنشاء دورة حياة الاتصالات وصيانتها (`*pgxpool.Pool`).
   - ضبط خصائص المحرك، ترجمة الأخطاء التخزينية، إدارة التراجع الأسي والتشويش، والتحقق من نبضات القلب (Health Check).
   - مستقلة تماماً عن أي منطق أعمال أو كينونات (Entities).
2. **طبقة المستودعات المحددة (`internal/storage/*`)**:
   - مسؤولة عن استعلامات SQL الخاصة بكيانات معينة (مستخدمين، طلبات، فواتير).
   - تعتمد على واجهة `postgres.DBTX` لتنفيذ الأوامر.
   - تستدعي `postgres.TranslateError` لعزل أخطاء المحرك عن بقية الطبقات.

```text
┌────────────────────────────────────────────────────────┐
│               Domain & Service Layers                  │

                            │ تستدعي
                            ▼
```

## 2. فلسفة تفضيل `pgx/v5` المباشر على `database/sql`

يوفر الانتقال إلى `pgx/v5` المباشر بدون محول `database/sql` مزايا حاسمة في مشاريع الإنتاج الكبرى:

1. **Prepared Statement Cache الشفاف**:
   يقوم `pgx` تلقائياً بتخزين الاستعلامات المحضرة مسبقاً (Prepared Statements) على مستوى كل اتصال، دون الحاجة لأي كود إضافي، مما يخفض زمن الاستجابة واستهلاك المعالج بنسبة تصل إلى 20-30%.
2. **استغلال بروتوكول PostgreSQL الثنائي (Binary Protocol)**:
   يتخطى التشفير النصي للأرقام والتواريخ والأشكال المكانية والمصفوفات ويوفر تحويلاً مباشراً وسريعاً للأنواع.
3. **الدعم الأصلي للعمليات الدفعية (`CopyFrom` و `SendBatch`)**:
   إمكانية إدخال ملايين السجلات في ثوانٍ باستخدام بروتوكول `COPY`، وتنفيذ عدة استعلامات في رحلة شبكية واحدة عبر خط أنابيب الدُفعات (Batching).
4. **تكامل كامل مع ميزات PostgreSQL المتقدمة**:
   دعم `LISTEN/NOTIFY` المباشر للأحداث الفورية، والإقفالات الإرشادية (Advisory Locks)، ونمط Unnest للأوامر المجمعة.

## 3. هندسة وتوليف مجمع اتصالات الإنتاج (`Pool Sizing Invariants`)

### المعادلة الذهبية لحجم المجمع

في بيئات الحاويات المصغرة (Kubernetes / Cloud Run)، يُعد تخصيص عدد هائل من الاتصالات لكل حاوية خطأً فادحاً يؤدي إلى استنزاف ذاكرة خادم PostgreSQL وزيادة التنافس على الأنوية (Context Switching Overhead).

المعادلة القياسية الموصى بها عالمياً لحساب إجمالي اتصالات الخادم:

$$\text{Total Connections} = (\text{CPU Cores} \times 2) + \text{Effective Spindle Count}$$

وعند توزيع هذا الإجمالي على نسخ التطبيق المتعددة ($N$ Instances):

$$\text{MaxConns per Pod} = \left\lfloor \frac{\text{PostgreSQL max\_connections} - \text{Superuser Buffer}}{N \times 1.25} \right\rfloor$$

### إعدادات المعلمات في `postgres.Config`

| المعلمة | القيمة الافتراضية | التوصيف الهندسي |
| :--- | :--- | :--- |
| `MaxConns` | `25` | الحد الأقصى للاتصالات المتزامنة المسموح للمجمع بفتحها مع الخادم. |
| `MinConns` | `5` | الحد الأدنى من الاتصالات الجاهزة والمفتوحة باستمرار لتفادي زمن تأخير مصافحة TCP/TLS عند بدء الحمل. |
| `MaxConnLifetime` | `1h` | العمر الأقصى للاتصال قبل إغلاقه واستبداله، لتفادي تسرب الذاكرة ولضمان توزيع الحمل عبر خوادم الـ Proxy أو الـ Aurora Read Replicas. |
| `MaxConnIdleTime` | `5m` | المدة الزمنية المسموح بها للاتصال الزائد بالبقاء خاملاً قبل إغلاقه وإعادته لمستوى `MinConns`. |
| `HealthCheckPeriod` | `30s` | الفاصل الزمني الذي يقوم فيه المجمع باختبار الاتصالات الخاملة في الخلفية للتأكد من أنها لم تنقطع بجدران الحماية (Firewall Silent Drops). |

## 4. دورة حياة المجمع وإلغاء الإنشاء الفاشل (Fail-Fast Initialization)

عند استدعاء `postgres.NewPool(ctx, cfg, logger)`:

1. يتم فحص نص الاتصال وتوليف المعلمات.
2. يتم تشغيل فحص اتصال صارم `pool.Ping(ctx)` مع مهلة زمنية قصيرة (5 ثوانٍ).
3. إذا فشل الاختبار، يتم إغلاق المجمع فوراً وإعادة خطأ مشفر `platformerr.CodeUnavailable`.
4. عند إيقاف تشغيل الخدمة، يتم استدعاء `postgres.ClosePool(pool, logger)` لإنهاء العمليات المعلقة وإغلاق المقابس بسلام.
